<design_notes>
Architecture decision (reasoned deviation from the literal "client component" phrasing in the request):
`WhatsAppFloatingButton` is an **async server component**, exactly mirroring how `GlobalHeader` (server) delegates to `WhatsAppCta` (client). The client boundary is already `WhatsAppTrackedLink` — the wrapper itself does NOT need `"use client"`. This lets the wrapper fetch `waHref` via `getSiteBrand()` and the aria-label via `getTranslations("contact")` server-side, with ZERO prop drilling from the layout (self-contained, same as `GlobalHeader`). This honors the intent — reuse `WhatsAppTrackedLink` for tracking, fetch `waHref` the same way `GlobalHeader` does — while staying consistent with the codebase's existing server-wrapper pattern.

Why NOT reuse `WhatsAppCta` directly: it hardcodes `location` to `"header"`/`"mobile-nav"` based on `iconOnly`, so it cannot emit `location="floating-button"` without modifying a component the request forbids touching. `WhatsAppTrackedLink` accepts `location` as a prop and is the correct reuse.

RTL: use logical `end-md` (inline-end, mirrors with `dir`) + vertical `bottom-md` (no mirroring needed). Never `right-*`. `npm run lint:rtl` must stay green.

z-index: `z-40` — above page content, matches the header, and stays below the mobile-nav sheet/dropdown overlays (`z-50`) so an open mobile nav correctly covers the button.

Color: use the site's brand green `bg-primary-700` + `hover:bg-primary-500` (not WhatsApp neon `#25D366`) — request says "WhatsApp-appropriate but consistent with the site's existing tokens." Elevation via the existing `shadow-card-hover` token (no new shadow). Focus ring `focus-visible:ring-accent-600` matches the header WhatsApp button.
</design_notes>
