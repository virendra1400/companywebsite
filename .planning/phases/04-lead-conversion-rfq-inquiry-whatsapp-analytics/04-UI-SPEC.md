# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This EXTENDS the locked Phase 1-3 design system** (see `01-UI-SPEC.md`, `02-UI-SPEC.md`, `03-UI-SPEC.md`). Tokens, fonts, colors, spacing scale, type scale, and the RTL contract are **not re-derived**. Phase 4 makes the existing `ContactForm`/`ContactBlockView` stub real (LEAD-01/02/03/04/05), adds a persistent header WhatsApp CTA (LEAD-06/D-05), and adds an analytics event-firing layer + optional consent banner (LEAD-07/ANALY-01). No new page is created — every change lands inside existing chrome (`GlobalHeader`, `MobileNavPanel`) and the existing `/contact` route.

## Skill Guidance Applied

Per coordinator instruction, `design-taste-frontend/SKILL.md` and `minimalist-ui/SKILL.md` (both installed at `.agents/skills/`) were read and reconciled against this project's already-locked Phase 1 brand system before writing this contract.

**design-taste-frontend — applicable parts used:**
- **§13 Out of Scope** explicitly excludes "multi-step forms" from the skill's landing-page/hero/bento/marquee directives — correctly so: this phase is form/CTA engineering inside an existing branded system, not a new landing page. None of §4.7 (hero rules), §4.3 (anti-center-bias), §9.F (eyebrow/marquee/section-numbering tells) apply here; they are not referenced below.
- **§4.5 Interactive UI States** applied directly: full loading/error/success cycle specified for the form (not "static success only"), tactile `:active` feedback on the submit button, explicit **Button Contrast Check** and **Form Contrast Check** (all new field labels/errors verified against the existing WCAG-AA-passing token pairs, no new colors introduced).
- **§4.5 CTA Button Wrap Ban** and **§4.5 No Duplicate CTA Intent** applied as a real finding: the codebase currently has TWO different WhatsApp CTA labels in production — `"Chat on WhatsApp"` (CTA band, 3 call sites, hardcoded) vs. `"Message us on WhatsApp"` (`contact.whatsappLabel` in the message catalogs, used by `ContactBlockView`). This is a same-intent/different-label violation. **Resolution below in Copywriting Contract:** standardize on `"Chat on WhatsApp"` everywhere, including updating `contact.whatsappLabel`/`whatsappAria`, since this phase already touches WhatsApp-adjacent copy (D-05).
- **§4.6 Data & Form Patterns** applied: label above input, error text below, `gap-md` between fields (project's own token, not the skill's literal `gap-2`), no placeholder-as-label anywhere in the new fields — matches the existing `ContactForm.tsx` pattern exactly, so new fields are indistinguishable in style from the old ones.
- **§9.D / §9.G** applied to every string in the Copywriting Contract below: no filler verbs ("elevate", "seamless"), no fake-precise numbers, **zero em-dashes** (all rewritten with periods/commas/hyphens).
- **§3.C Icons override applied, not the discouraged default:** the skill discourages Lucide by default, but explicitly allows it "when the project already depends on it" — this project's `components.json` locks `iconLibrary: lucide` and every existing chrome component (`Menu`, `Globe`, `MapPin`, `Phone`, `Mail`, `ChevronRight`) already uses it. Lucide stays. Similarly, the existing hand-authored `WhatsAppIcon` SVG (Phase 2, `ContactBlockView.tsx`) is kept and **promoted to a shared component** rather than replaced — it's exactly the skill's own narrow exception ("a single, simple geometric mark," brand-recognizable, no dedicated Lucide glyph exists), not a new violation.
- **Not applicable / not used:** dial system (§1), hero rules (§4.7), bento/marquee/scroll-hijack patterns (§5), image-asset strategy (§4.8) — none of this phase's surfaces are hero or landing-page composition.

**minimalist-ui — reconciled, not blindly followed:** this skill's concrete mandates (ban Lucide, ban existing brand fonts, force a specific warm-monochrome-plus-pastel palette, ban `rounded-full`) directly conflict with the Phase-1-locked forest-green/gold IBM Plex Sans identity (see `CLAUDE.md`/`PROJECT.md`) and are **not applied** — a premium B2B export site with a already-shipped, checker-approved brand system does not get re-skinned by a generic aesthetic preset mid-project. What **is** compatible and *is* applied: the skill's restraint principles already match Phase 1's own token choices (no shadow tokens defined in `globals.css` at all; sections are separated by flat background alternation, not elevation) — so new surfaces this phase (honeypot field, Turnstile widget slot, WhatsApp header button, consent banner) use **zero new box-shadow, zero gradients**, consistent with both the skill's restraint spirit and the pre-existing tokens.

## Component Inventory

### 1. `WhatsAppIcon` — promote to shared component (no new dependency)

**Extract** the existing hand-authored SVG from `src/components/blocks/ContactBlockView.tsx` (lines 13-19) into `src/components/icons/WhatsAppIcon.tsx`, exported and imported by every WhatsApp-CTA call site (`ContactBlockView`, the new `GlobalHeader`/`MobileNavPanel` CTA, and — optionally — the existing CTA-band secondary-CTA rendering if it wants the brand glyph instead of a generic label-only link). One component, one SVG path, zero duplication, zero new icon-library dependency. This directly satisfies both skills' "reuse real design systems, don't hand-roll a second version" principle.

### 2. Header WhatsApp CTA (new, D-05)

Sits in `GlobalHeader` and `MobileNavPanel`, in the exact same structural slot the existing "Request a Quote" button already occupies (not a floating action button — explicitly rejected per D-05).

**Desktop (`GlobalHeader`, `sm:` and up, same breakpoint as the existing Request-a-Quote button):**
- Icon-only `Button variant="outline" size="icon"` — `className="size-11 border-primary-700 text-primary-700 hover:bg-primary-100 focus-visible:ring-accent-600"` (44px touch target per the Spacing exception above).
- `<WhatsAppIcon className="size-4" />` inside, `aria-hidden="true"` on the icon (same pattern as every other icon-in-button in the codebase).
- `aria-label={t("contact.whatsappAria")}` on the `<a>`/`Button asChild` wrapper — never icon-only without an accessible name (Phase 2's own explicit rule, reapplied).
- **Order in the header row:** LanguageSwitcher → WhatsApp icon button → "Request a Quote" (primary, filled) → MobileNavPanel trigger. Secondary/lighter-weight action (WhatsApp) sits before the primary filled CTA, which stays the rightmost/most-emphasized element — unchanged visual hierarchy, WhatsApp is additive, not competing.
- `href={waHref}` from `getSiteBrand()` — never hardcoded, per the CONTEXT.md canonical-refs rule.
- `target="_blank" rel="noopener noreferrer"`.

**Mobile (`MobileNavPanel` sheet, same footer area as the existing "Request a Quote" button):**
- Full-width `Button variant="outline"` (not icon-only — there's vertical room in the sheet) with visible label + icon: `<WhatsAppIcon className="size-4" /> {t("contact.whatsappLabel")}` — same 44px minimum height as the existing sheet Button.
- Positioned directly above the existing "Request a Quote" button, same `gap-lg` sheet rhythm, so the sheet footer reads: WhatsApp (outline) → Request a Quote (filled primary).

**Analytics wiring (visual contract note, not architecture):** the `onClick` handler on every WhatsApp CTA in the site (header, hero secondary CTA, product-detail CTA band, catalog CTA band, `ContactBlockView`) fires the single `whatsapp_click` event before the browser navigates to `wa.me` — this is why promoting a shared `WhatsAppIcon`-consuming CTA component (rather than 5 separate hand-wired anchors) matters: one call site for the event-firing logic, not five.

### 3. Shared Inquiry/RFQ Form — extends `ContactForm.tsx` in place (D-01, D-02, D-03, D-04)

One form, one schema (`contactSchema`), rendered inside the existing `ContactBlockView` two-column layout — no new page, no new route. Mode is derived client-side from `useSearchParams().get("product")` (already the plan per CONTEXT.md code_context).

**Field order, top to bottom (single `grid gap-md` column, matching the existing form exactly — no new grid density introduced):**

| # | Field | Mode | Input | Notes |
|---|---|---|---|---|
| 1 | Product context banner | RFQ only | Non-input `div`, `bg-primary-100 rounded-md px-md py-sm text-body` | "Requesting a quote for **{productName}**" (Body-600 for the name). **Not** rendered as a bordered `Input` — a boxed input visually implies editability, which D-03 explicitly rejects. Functionally paired with a `<input type="hidden">` registered via `register("product")` so the value still submits; the visible banner is presentation-only. |
| 2 | Name | both | `Input`, required | unchanged |
| 3 | Company | both | `Input`, required | unchanged |
| 4 | Country | both | `Input`, required | unchanged — visitor/company location (D-04) |
| 5-6 | Email / Phone | both | `Input` pair, `grid grid-cols-1 sm:grid-cols-2 gap-md` | Both individually optional; **combined rule:** at least one of the two must be filled, surfaced as one error string anchored under the Phone field (see Copywriting Contract) — not two separate "required" errors on two optional-looking fields, which would read as a broken validation UX. |
| 7 | "Quote Details" subheading | RFQ only | Label-600 text, `mt-sm` | Visually separates general-contact fields from RFQ-qualifying fields |
| 8-10 | Quantity / Destination Country / Incoterm | RFQ only | 3-field group, `grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-md` | See field-level detail below |
| 11 | Message | both | `Textarea rows={5}`, required, min 20 chars | unchanged |
| 12 | Honeypot | both (always rendered, always empty for real users) | See detail below | Not a visible "field" to sighted/keyboard/screen-reader users |
| 13 | Turnstile widget | both | Cloudflare-rendered widget slot | Managed mode (visible-when-needed, mostly invisible) — Cloudflare's own recommended default for a conversion form; sits in normal `gap-md` rhythm directly above the submit button, no custom chrome needed around it |
| 14 | Submit button | both | `Button`, label varies by mode (see Copywriting Contract) | Loading state: inline spinner + `disabled` + label swap (see below) |
| 15 | Result banner | both | Success (`bg-primary-100`) or error (`bg-destructive/10 text-destructive border border-destructive`) panel, appears **above** the submit button on failure (fields retain input, user can retry) or **replaces** the form in place on success (existing pattern, unchanged from Phase 2's stub) | |

**Field-level detail:**

- **Quantity:** `Input`, NOT `type="number"` — export quantities are expressed in mixed units ("20 MT", "1 x 20ft container"), and a numeric spinner input actively fights that. Placeholder-as-label is banned (per skill guidance) — use a `FormDescription`/helper `<p>` below the label instead: "e.g. 20 MT, or 1 x 20ft container" (Label token, `text-neutral-600`).
- **Destination Country:** plain `Input`, same treatment as the existing `Country` field. **Claude's Discretion, resolved here:** NOT upgraded to a country-select/combobox this phase, despite Phase 2's comment flagging a "full country picker" as "RFQ-form territory." A 195-country picker needs a maintained list translated across 4 locales (real i18n cost) for a field sales staff read and normalize manually; building it now is scope creep the requirements don't demand (LEAD-02 only asks for "destination country" as a qualifying field, not a validated picker). Symmetric plain-text treatment with `Country` keeps the form visually and behaviorally consistent.
- **Incoterm:** new shadcn `Select` (closed enum, appropriate for a categorical business term where free text produces messy sales data). 11 Incoterms 2020 codes, each option formatted `"{CODE} ({Full Name})"` — no em-dash separator: EXW (Ex Works), FCA (Free Carrier), CPT (Carriage Paid To), CIP (Carriage and Insurance Paid To), DAP (Delivered at Place), DPU (Delivered at Place Unloaded), DDP (Delivered Duty Paid), FAS (Free Alongside Ship), FOB (Free on Board), CFR (Cost and Freight), CIF (Cost, Insurance and Freight). Optional field (buyer may not know their incoterm yet) — placeholder option "Not sure yet" is a real selectable option, not a disabled placeholder-as-label.
- **Honeypot:** a real, always-present, always-empty-for-humans field. `aria-hidden="true"`, `tabIndex={-1}`, `autoComplete="off"`, positioned off-screen (`className="absolute -left-[9999px] top-auto h-px w-px overflow-hidden"` — off-canvas, not `display:none`/`visibility:hidden`, since some bots specifically skip those two). Field name/label use a plausible decoy a bot would want to fill, e.g. label text "Company Website" bound to a schema key distinct from the real `company` field (e.g. `companyWebsite`). **If filled:** the server action silently treats the submission as accepted (shows the normal success banner) but does not send the email — never reveal detection to the sender.

**Loading/success/error cycle (this is the form's FIRST real async call — Phase 2's stub only set local state):**
- **Loading:** on submit, the button shows an inline spinner (reuse `lucide`'s `Loader2` with a `animate-spin` class — the one motion exception in this phase, purely a spinner, not decorative), `disabled`, label swaps to a loading variant (see Copywriting Contract), all fields become `readOnly` (not `disabled`, so screen readers keep announcing them and values aren't dropped if the request needs re-submission) during the in-flight request.
- **Success:** existing Phase 2 pattern reused — form replaced in-place by an inline `role="status"` confirmation panel, `bg-primary-100`, Body token.
- **Error (server/network/rate-limit failure):** NEW this phase — a destructive-styled banner appears above the submit button (form is NOT replaced, no data loss), button re-enables, user can retry immediately without re-typing.

## Consent Banner (conditional, ANALY-01)

Only rendered if the GA4+GTM analytics path is chosen (deferred decision, per CONTEXT.md). If Plausible is chosen instead (cookieless), this component does not render at all — no dead code shipped either way, the planner gates it behind whichever vendor lands.

- Fixed bottom bar, `bg-primary-900 text-white`, full-width, `px-md py-md md:px-lg` — matches the footer's dark-surface color exactly (not a new color).
- No modal/blocking overlay — a premium B2B site should not gate content behind a cookie wall for a traffic-analytics-only use case.
- Content: body text (Label token) + two `Button`s (`Accept` — filled primary; `Decline` — outline, same treatment as other outline buttons in this spec) stacked on mobile, inline row on `sm:` and up.
- No link to a `/privacy` page — that route does not exist yet in this project's page set (PAGE/TRUST requirements don't include it); do not fabricate a dead link. If/when a privacy policy page is built, the copy gets a link added then.
- `Accept` sets GTM consent state to granted; `Decline` sets it to denied and suppresses the GA4 tag. Both choices dismiss the banner and persist (localStorage or cookie), so it does not re-appear on every page.
