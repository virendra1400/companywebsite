<objective>
Complete the RFQ conversion path: when `/contact?product=X` carries a product, render the RFQ-qualifying fields (read-only product banner via D-03, Quantity, Destination Country per D-04, Incoterm Select) conditionally on top of the shared inquiry form, and fire `rfq_submit`. One form, one schema, one route (D-02) — the query param drives mode.

After this plan a real user who clicks "Request a Quote" from a product page lands on `/contact?product=slug` and submits a per-product RFQ with qualifying fields, delivered through the same 04-02 pipeline and tracked as a distinct `rfq_submit` event.

Purpose: LEAD-02 (per-product RFQ) + the RFQ half of LEAD-07.
Output: shadcn `select`, RFQ conditional fields in `ContactForm.tsx`, RFQ catalog copy, RFQ e2e + RFQ-payload unit assertion.
</objective>

| product query param → form | Untrusted URL param populates the read-only product context |
| bot → RFQ form | RFQ mode uses the same public submission entry as inquiry |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Denial of Service / Repudiation | RFQ submission path | high | mitigate | RFQ mode reuses the same honeypot + rate-limit + Turnstile pipeline (04-02/04-03) — no separate unguarded entry point |
| T-04-06 | Information Disclosure | rfq_submit event params | medium | mitigate | rfq_submit carries only the product slug; product/quantity/destination/incoterm and all PII stay out of analytics params |
| T-04-07 | Tampering | product/productName URL params rendered in banner | low | accept | Params are display-only text in a React-escaped banner and a hidden input echoed to the server; the slug is not used for any privileged lookup in this phase (React auto-escapes, no injection sink) |
</threat_model>
