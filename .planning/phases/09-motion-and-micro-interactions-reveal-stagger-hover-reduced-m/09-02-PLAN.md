Create `tests/e2e/reduced-motion.spec.ts` targeting `/` (the homepage — 11 CMS blocks, so it has plenty of below-the-fold reveal wrappers). Scope this file to reveal/reduced-motion only; the accordion and button `:active` assertions live in `tests/e2e/contact.spec.ts` and are owned by plan 09-04, so do not add them here (that file split is what lets 09-02 and 09-04 run in the same wave without touching the same file).

Critical API note: assert on `getComputedStyle(el).translate`, never `.transform`. Tailwind v4 compiles `translate-y-6` to the standalone `translate` CSS property (verified against the installed compiler, 4.3.2), so `.transform` reads `none` on a correctly-implemented reveal wrapper and a transform-based assertion would pass vacuously or fail misleadingly.

Write these tests:

1. **Reduced motion: content visible immediately, motion gone.** `await page.emulateMedia({ reducedMotion: "reduce" })`, then `page.goto("/")`. Take the LAST `[data-motion="reveal"]` on the page (deepest below the fold) and, without scrolling, assert it eventually carries `data-revealed="true"`, that its computed `opacity` is `"1"`, and that its computed `transitionDuration` is `"0s"`. That triple is the whole D-12 contract for scroll-reveal: present, visible, unanimated.

2. **No preference: hidden until scrolled, then revealed.** `await page.emulateMedia({ reducedMotion: "no-preference" })`, then `page.goto("/")`. Take the last `[data-motion="reveal"]`, assert its computed `opacity` is `"0"` and it has no `data-revealed` attribute before any scrolling. Then `scrollIntoViewIfNeeded()` on it and assert it gains `data-revealed="true"` and computed `opacity` `"1"`.

3. **Zero replay.** Continuing from the same revealed element (or a fresh navigation that scrolls it into view first): scroll back to the top with `page.evaluate(() => window.scrollTo(0, 0))`, wait for the transition window to pass, then scroll the element into view again. Assert `data-revealed` is still `"true"` and computed `opacity` is still `"1"` — it never returned to the hidden state (D-06).

4. **Hero is never gated.** `page.goto("/")` with no reduced-motion preference. Assert `page.getByTestId("hero")` is visible and that, evaluated in the browser, the hero element has no `[data-motion="reveal"]` ancestor (`el.closest('[data-motion="reveal"]') === null`). Also assert the hero's own computed `opacity` is `"1"` on first paint. This is the LCP guard from D-07 and it must fail loudly if someone later removes the `blockType === "hero"` short-circuit.

5. **tw-animate-css actually resolved.** In `page.evaluate`, create a detached-then-appended `div`, set its `className` to `animate-in fade-in-0`, append to `document.body`, read `getComputedStyle(el).animationName`, remove the element, and return the value. Assert it is not `"none"`. This is the only cheap deterministic proof that plan 09-01's `@import "tw-animate-css"` line took effect and therefore that the previously dead shadcn Sheet/DropdownMenu/Select entrance classes — i.e. D-08's mobile-nav polish — now resolve to real keyframes. Without this assertion the D-08 fix is unverifiable, since it involves no component edit at all.

Keep the spec free of arbitrary sleeps where a Playwright auto-waiting assertion will do; where the zero-replay test genuinely needs to let a 600ms transition finish, use an explicit short `page.waitForTimeout` with a comment saying why, rather than a bare magic number.
