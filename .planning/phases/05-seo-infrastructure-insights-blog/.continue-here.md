## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Executor-reported `expected_base` can be wrong | One Wave-1 executor's `<worktree_metadata>` block self-reported `expected_base` as its OWN last commit hash instead of the true fork point off main | advisory | Before running `worktree.cleanup-wave`, cross-check any suspicious `expected_base` (e.g. one that matches a commit belonging to that same branch) against `git merge-base <branch> main`; correct the manifest JSON directly if they disagree, then retry cleanup |
| Payload SQLite push never fires under `next build` | `next build` sets `NODE_ENV=production`; Payload's sqlite adapter only runs `pushDevSchema` when `NODE_ENV !== 'production'` (node_modules/@payloadcms/db-sqlite/dist/connect.js:50) — setting `push: true` in payload.config.ts does NOT override this and is a no-op | advisory | If `next build` fails with `SQLITE_ERROR: no such table: ...` after a plan adds/changes a Payload collection or global field, run a one-off script (see Infrastructure State below) that imports `src/payload.config.ts` and calls `getPayload()` under normal (non-production) `NODE_ENV` to sync `payload.db` on disk, then re-run the build. Delete the one-off script after use — it is not part of the repo. |
| Sibling plans marking different REQUIREMENTS.md rows both cause merge conflicts | 05-02 and 05-03 both edited the same `SEO (SEO)` checklist block and the traceability table in `.planning/REQUIREMENTS.md`, each marking a different requirement ID `[x]` | advisory | When `worktree.cleanup-wave` reports `merge_failed` with a conflict in `.planning/REQUIREMENTS.md`, it is almost always two adjacent `- [ ]`/`[x]` lines or two table rows — resolve by keeping BOTH sides' `[x]` marks (union, not either/or), remove conflict markers, `git add`, `git commit --no-edit` |
