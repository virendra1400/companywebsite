# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This EXTENDS the locked Phase 1-4 design system** (see `01-UI-SPEC.md` … `04-UI-SPEC.md`). Tokens, fonts, colors, spacing scale, type scale, and the RTL contract are **not re-derived**.

**Scope note — this phase's visible UI surface is narrow.** SEO-01…05 (metadata, hreflang, sitemap, JSON-LD) are invisible plumbing — zero new visual component, verified via view-source/crawl-audit/rich-results-test, not a design contract concern. The ONLY new visitor-facing UI this phase introduces is: (1) a new "Insights" nav item in the existing `GlobalHeader`/`MobileNavPanel`, (2) an `/insights` list page, and (3) an `/insights/[slug]` article page. Everything below covers only these three surfaces; the rest of the phase is out of this document's scope by design.

## RTL & Locale Contract — Phase 5 Extensions

Everything in Phase 1-4's RTL contract applies unchanged (logical properties only, `dir` server-set, Western numerals for `ar`, `<bdi>` for mixed BiDi content). Additions specific to Insights:

| Concern | Rule |
|---|---|
| **Cover image does not mirror** | Same "photography carries no inherent reading-direction" rule as the Product gallery (Phase 3) — the article cover image and InsightCard cover thumbnail render identically in `ltr` and `rtl`. |
| **Byline date must force Western numerals** | `FOUND-03` requires non-mirrored numerals for Arabic. This repo's `src/i18n/request.ts` currently declares a `formats.number.latn` entry (used by `format.number(n, "latn")`) but **no equivalent `formats.dateTime.latn` entry** — the planner MUST add one (`dateTime: { latn: { numberingSystem: "latn", dateStyle: "long" } }`, mirroring the existing `number.latn` shape exactly) and call it via `format.dateTime(date, "latn")` for the byline/card-meta date. Do not call bare `Intl.DateTimeFormat(locale, ...)` without forcing `numberingSystem: "latn"` — Arabic defaults to Arabic-Indic digits otherwise. |
| **Breadcrumb chevron mirrors** | Identical to Product detail's breadcrumb: `<ChevronRight aria-hidden className="size-4 rtl:-scale-x-100" />` between crumb segments — reused verbatim, not reinvented. |
| **Article body (richText) uses logical alignment only** | Payload lexical output renders plain paragraphs — no physical `text-left`/`text-right` is introduced; the container itself uses `text-start` if any explicit alignment class is added (none is needed by default). |
| **Meta row (category badge + byline) wraps via logical `gap-sm flex-wrap`** | No manual reordering — `dir` handles inline-start/end automatically, same as every other chrome row in this project. |
| **Article/category slugs stay Latin/ASCII** | Standard CMS-slug practice, unchanged from Products — only the visible article **title** localizes, never the URL segment (D-06). |

## Component Inventory

### 1. GlobalHeader / MobileNavPanel — new "Insights" nav item (D-05)

One more entry in the existing fixed `NAV_KEYS`/`NAV_HREFS` arrays in **both** `GlobalHeader.tsx` and `MobileNavPanel.tsx` (these two files currently duplicate the nav list — no new pattern, just one more key in each):

```
NAV_KEYS: [..., "company", "contact"] → [..., "company", "insights", "contact"]
NAV_HREFS.insights = "/insights"
```

Position: between "Company" and "Contact" (matches the "top-level, fixed route" placement rule already governing every other item — D-05 explicitly calls this a real top-level route, not a dropdown/submenu). Label: `t("insights")` — a new `nav.insights` message key, value `"Insights"` in `en.json`, and the **same English placeholder string** in `ar.json`/`fr.json`/`ru.json` for now (this project's existing mixed pattern already leaves several nav keys — `home`, `about`, `export`, `company` — untranslated in ar/fr/ru; `insights` follows that same precedent, not a new gap).

No visual/style change to `GlobalHeader`/`MobileNavPanel` beyond the one added link — no new component.

### 2. InsightCard (Insights list grid item)

Reuses the shadcn `Card` primitive — same base family as `ProductCard`/`CertCard`, for cross-catalog visual consistency.

| Field rendered | Source | Notes |
|---|---|---|
| Cover image | `coverImage` (required field, always present) | `AspectRatio ratio={16/9}` (editorial/banner proportion — deliberately different from ProductCard's `4/3` product-photography proportion, since a cover image is a banner, not a product shot), `object-cover`, `next/image` `sizes="(min-width: 1024px) 33vw, (min-width: 768px) 50vw, 100vw"` |
| Meta row (category · date) | `category.name` (relationship, may be absent — D-02's field is not required) + `publishedDate` | Label token, `text-neutral-600`. If `category` is absent, meta row shows the date alone (no empty "· " dangling separator — conditionally render the separator, not just the category). |
| Title | `title` (localized) | Body-600, `line-clamp-2` |
| Excerpt | `excerpt` (localized) | Body, `line-clamp-3` |

**Layout:** entire card is a single tap target (`Link` to `/insights/[slug]`), same "whole card clickable, not just the title" rule as ProductCard. `Card` padding `p-md` mobile / `p-lg` desktop. Hover/focus: same subtle `-translate-y-[1px]` + shadow bump + `accent-600` focus-visible ring as ProductCard — zero new interaction pattern.

**Grid:** `grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-md md:gap-lg` — one column narrower than ProductCard's `2/3/4` grid at every breakpoint, because an article card carries more text (title + 3-line excerpt) and needs more per-card width to stay readable; a 4-up desktop grid would crush the excerpt into an unreadable strip.

**Cover image absent (defensive only — `coverImage` is a required field, this state should not occur in practice):** same `bg-neutral-100` + centered `ImageOff` placeholder as ProductCard, for defense-in-depth consistency, not because it's an expected state.

### 3. InsightsIndex (page: `/insights`)

Composition, rendered inside existing chrome:

```
Hero (compact variant, "Insights")
→ flat grid of InsightCard, reverse-chronological by publishedDate (no category-grouped sections,
  no filter UI — see resolved discretion below)
→ CTABand (reused verbatim, "Ready to Source With Confidence?" / "Request a Quote" / "Chat on WhatsApp" —
  same heading already used on Product detail, no new copy invented for this page)
```

**Resolved discretion — no category filter UI in v1:** D-02's `category` field exists for "grouping/filtering," but BLOG-01 only requires "visitor can browse a list and read an article" — no success criterion requires a filter control. InsightCard shows the category as a scannable meta-row badge only; a click-to-filter chip row (à la the catalog's category anchor-nav) is explicitly deferred, not silently dropped — add it later if the article count grows large enough to need it. Keeps this phase's UI surface as narrow as its actual requirements.

**Empty state (zero published articles — the expected pre-launch state, per BLOG-01's "structure ready" framing):** whole-page empty state, same shape as the catalog's pre-seed empty state (Heading + Body + contact link) — see Copywriting Contract.

### 4. InsightArticle (page: `/insights/[slug]`)

Composition:

```
PageHeader (bg-white, py-lg md:py-xl — same lightweight treatment as Product detail's PageHeader,
  NOT a full photographic Hero, for the same "one focal point per page" reason Phase 3 established
  — the cover image below is this page's visual anchor):
    - Breadcrumb: "Insights / [Article title]" (Label token, ChevronRight rtl:-scale-x-100)
      — NO category crumb (resolved discretion below)
    - Title <h1> (Display token)
    - Meta row: category Badge (if present) + byline "By {author} · {date}" (Label, text-neutral-600)
→ Cover image banner (bg-white, contained to max-w-[1280px], AspectRatio 16/9, object-cover,
  next/image priority — this page's LCP candidate, replacing the gallery's role on Product detail)
→ Body region (max-w-[720px] mx-auto, py-lg md:py-xl): richText via the exact same
  <RichText data={article.body} /> + container convention already used for Product description
→ CTABand (reused verbatim, "Ready to Source With Confidence?" — same instance as InsightsIndex's,
  no new copy invented)
```

**Resolved discretion — no category crumb in the breadcrumb:** unlike Product detail's breadcrumb (`Products / [Category] / [Product name]`), the Insights article breadcrumb is `Insights / [Article title]` only. Reason: D-11 explicitly frames the article's one natural parent as "the insights list," not a category (categories have no dedicated archive page in this phase — there's nothing for a category crumb to link to). This also keeps the visual breadcrumb an exact match for the `BreadcrumbList` JSON-LD emitted per D-11 (2 levels: Insights → article), rather than inventing a third, unlinkable crumb segment.

**Locale fallback:** both `/insights` and `/insights/[slug]` reuse `LocaleFallbackNotice` verbatim (same component, same placement at the top of `<main>`) whenever `isTranslated` is false — identical to every other content page in this project.

**Article-not-found (invalid/unpublished slug):** same shape as Product detail's not-found state — see Copywriting Contract.
